# 06. Comprehensive Refactoring (종합 리팩터링)

## 1. 코드의 목적

- 도서 대출 기록을 기반으로 연체료 계산
- 반납 완료된 도서만 처리
- VIP 회원은 연체료 면제
- 연체일에 따라 사용자별 연체료 계산
- 사용자별 연체료와 전체 합계 출력

### 비즈니스 규칙

- 미반납 도서: 계산 및 출력에서 제외
- 연체일 0일 이하: 연체료 0원
- VIP 회원: 연체료 0원
- 일반 회원: 연체일 × 500원

## 2. 발견한 Code Smell

| Code Smell                | 문제점                                           | 개선 방법                            |
| ------------------------- | ------------------------------------------------ | ------------------------------------ |
| Poor Naming               | `doStuff`, `x`, `a`, `t` 등 의미가 불분명한 이름 | 역할이 명확한 메서드명과 변수명 사용 |
| Deep Nesting              | `if` 조건문이 3단계로 중첩                       | Guard Clause 활용                    |
| Redundant Comparison      | `== true`를 사용한 불필요한 비교                 | Boolean 값 직접 검사                 |
| Duplicate Code            | 사용자별 연체료 출력 코드 중복                   | 출력 메서드로 통합                   |
| Magic Number              | 연체료 `500`을 직접 사용                         | `DAILY_LATE_FEE` 상수 정의           |
| Multiple Responsibilities | 하나의 메서드에서 검증, 계산, 출력 수행          | 메서드 책임 분리                     |

## 3. 리팩터링 결과

### 1. Naming 개선

- `doStuff` → 역할별 메서드로 분리
- `x` → `loans`: 대출 기록 배열
- `a` → `loan`: 개별 대출 기록
- `t` → `total_fee`: 전체 연체료
- `money` → `fee`: 개별 연체료

### 2. 메서드 책임 분리

| 메서드                | 책임                                |
| --------------------- | ----------------------------------- |
| `calculate_loan_fee`  | 개별 대출 기록의 연체료 계산        |
| `calculate_total_fee` | 반납 완료된 기록의 전체 연체료 합산 |
| `print_loan_summary`  | 사용자별 연체료 출력                |
| `print_loan_report`   | 전체 출력 과정 관리                 |

- 계산과 출력의 책임 분리
- 개별 계산 로직 재사용
- 테스트 및 유지보수 용이성 개선

### 3. Guard Clause 적용

- VIP 회원이면 즉시 0 반환
- 연체일이 0일 이하이면 즉시 0 반환
- 미반납 도서는 `next unless`로 순회 중 건너뜀
- 불필요한 조건문 중첩 제거

### 4. Enumerable 활용

- `select`: 반납 완료된 대출 기록 추출
- `sum`: 개별 연체료 합산
- 직접 합계를 누적하는 코드 단순화

### 5. Magic Number 개선

- `500` → `DAILY_LATE_FEE = 500`
- 연체료 정책을 상수명으로 명확히 표현
- 향후 연체료 변경 시 수정 위치 파악 용이

## 4. 개선 후 느낀 점

### 가독성 (Readability)

- 의미 있는 네이밍으로 코드의 목적 명확화
- Guard Clause로 조건문 중첩 감소
- 메서드별 책임을 쉽게 파악 가능

### 유지보수성 (Maintainability)

- 연체료 정책을 상수로 관리
- 계산 로직을 독립된 메서드로 분리
- 정책 변경 시 수정 범위를 줄일 수 있음

### 테스트 용이성 (Testability)

- 계산 메서드가 출력 없이 값을 반환
- `calculate_loan_fee`와 `calculate_total_fee`를 독립적으로 테스트 가능
- 향후 자동 테스트 작성 가능

### 추가 개선 사항

- 현재 사용자별 출력과 전체 합계 계산에서 연체료를 중복 계산
- 필요 시 계산 결과를 재사용하도록 개선 가능
- `nil`, 빈 배열, 음수 연체일 등의 예외 상황 검증 필요

## 5. 핵심 정리

- 좋은 코드는 단순히 짧은 코드가 아님
- 명확한 네이밍과 책임 분리가 중요
- Guard Clause로 가독성 개선 가능
- 리팩터링 과정에서 기존 동작 유지 필수
- 코드의 재사용성과 테스트 용이성까지 고려
